# Итоговые технические решения

Документ фиксирует ключевые технические решения, принятые при разработке
ИТ-ассистента технической поддержки АО «УК «БМЗ», с обоснованием выбора,
перечнем рассмотренных альтернатив, ограничениями и планом развития.
Предназначен для защиты дипломного проекта и передачи проекта в эксплуатацию.

---

## Ключевые принципы

1. **On-premise.** Все критичные компоненты (LLM, эмбеддинги, векторная БД,
   СУБД) работают локально. Данные не покидают контур предприятия.
2. **Минимум внешних зависимостей.** Внешние провайдеры подключаются только
   на этапе оценки качества (судья RAGAS) и могут быть заменены.
3. **Воспроизводимость.** Стек поднимается одной командой `docker compose up -d`.
4. **Ограниченные ресурсы.** Решения подобраны под одну GPU RTX 5070 (12 ГБ)
   и умеренные требования к RAM/CPU.
5. **Расширяемость.** Компоненты изолированы по слоям (`services/`, `routers/`,
   `agents/`), что позволяет менять LLM/эмбеддинги без переписывания логики.
6. **Объяснимость.** Каждое решение имеет измеримое обоснование
   (эксперимент, метрика, ссылка на артефакт).

## 1. LLM: локальная модель через Ollama

**Решение:** `frob/qwen3.5-instruct:4b`, сервер — Ollama, доступ через
OpenAI-совместимый эндпоинт `http://ollama:11434/v1`.

**Обоснование:**

- **On-premise.** Обращения сотрудников содержат внутренние данные
  (учётные записи, пути к сетевым ресурсам, конфигурации 1С). Передача их
  внешним провайдерам недопустима.
- **Ресурсы.** Модель 4B в квантованном виде занимает ~2.5–3 ГБ VRAM,
  что оставляет запас на RTX 5070 (12 ГБ) для эмбеддингов и реранкера.
- **OpenAI-совместимый API.** Позволяет использовать стандартный `openai`
  клиент и легко заменить модель/сервер без переписывания кода.
- **Русский язык.** Модель адекватно понимает русскоязычные запросы
  технической поддержки.
- **Быстрый fallback на CPU** при недоступности GPU.

**Альтернативы:**

| Модель / сервис | Почему не выбрана |
|---|---|
| GPT-4o-mini (OpenAI) | Внешний провайдер, данные уходят в облако |
| GigaChat / YandexGPT | Облачные, платные, ограничения по контенту |
| Qwen2.5:7b | Требует больше VRAM, качество на русском не выше для наших задач |
| Mistral 7B | Слабее на русском |
| vLLM | Избыточен для одной GPU, требует больше настройки |

## 2. Эмбеддинги: BAAI/bge-m3

**Решение:** `BAAI/bge-m3`, размерность **1024**, L2-нормализованные векторы.

**Обоснование:**

- **Мультиязычность.** Одинаково хорошо работает с русскими и английскими
  техническими терминами (1С, ERP, SSO, AD).
- **Dense + sparse из коробки.** Позволяет включить гибридный поиск
  (`RAG_USE_HYBRID=true`) без дополнительных моделей.
- **SOTA на MTEB** для мультиязычного retrieval.
- **Локальный инференс** через `llama-index-embeddings-huggingface` — без
  внешних API.
- **Размерность 1024** — компромисс между качеством и объёмом Qdrant
  (668 чанков × 1024 × 4 байта ≈ 2.7 МБ на коллекцию).

**Альтернативы:**

| Модель | Почему не выбрана |
|---|---|
| intfloat/multilingual-e5-small (384) | Ниже качество на длинных технических текстах |
| intfloat/multilingual-e5-large | Тяжелее, без выигрыша на нашем корпусе |
| rubert-tiny2 | Только русский, слабее на смешанных текстах |
| LaBSE | Заточена под sentence similarity, не retrieval |

**Эксперимент:** результаты сравнения — в [embedding.md](embedding.md).

## 3. Векторная БД: Qdrant

**Решение:** Qdrant, коллекция `rag_block_04`, метрика `COSINE`.

**Обоснование:**

- **Async-клиент.** `AsyncQdrantClient` органично встраивается в FastAPI.
- **Payload-фильтры.** Позволяют ограничивать поиск по `source`, `chunk_index`
  без потери скорости (фильтрация до ANN).
- **Простой деплой.** Один сервис в `compose.yaml`, REST/gRPC API,
  персистентность через volume.
- **Зрелость.** Активно развивается, документирован, стабилен.

**Эксперимент с метрикой.** Скрипт `scripts/compare_metrics.py` на 668 точках
и 5 запросах показал **5/5 совпадений** top-5 для `COSINE` и `DOT`. Это
объясняется L2-нормализацией векторов BGE-M3. Выбрана `COSINE` как более
устойчивая к возможной смене модели. Детали — в [vector_store.md](vector_store.md),
артефакт — в [metric_comparison.json](metric_comparison.json).

**Альтернативы:**

| БД | Почему не выбрана |
|---|---|
| pgvector | Медленнее на больших коллекциях, беднее фильтрация |
| Chroma | Проще, но слабее по перформансу и фичам |
| Milvus | Избыточен (etcd + minio), overkill для одной ноды |
| FAISS | In-memory, нет HTTP API и полноценной фильтрации |

## 4. Агентный слой: LangGraph

**Решение:** LangGraph с персистентными чекпоинтами (Postgres) и поддержкой
human-in-the-loop.

**Обоснование:**

- **HIL.** Агент приостанавливается перед действиями, требующими подтверждения
  (отправка письма, эскалация). Это критично для корпоративного ассистента.
- **State machine.** Явные узлы и переходы упрощают отладку и объяснение
  поведения на защите.
- **Стриминг.** Поддерживается из коробки — используется в `/agent/stream`.
- **Чекпоинты.** Перезапуск backend не теряет состояние диалога
  (`AGENT_CHECKPOINTER=postgres`).
- **Один агент с инструментами.** Минимально достаточная конфигурация:
  `search_knowledge_base`, `multiply` (демо), задел под новые инструменты.

**Альтернативы:**

| Решение | Почему не выбрано |
|---|---|
| LangChain AgentExecutor | Нет HIL и персистентности из коробки |
| CrewAI | Ориентирован на мультиагентность, избыточен |
| AutoGen | Сложнее для одиночного агента |
| Свой ReAct-цикл | Дороже поддерживать, теряются готовые фичи |

## 5. RAG-фреймворк: LlamaIndex

**Решение:** LlamaIndex для построения индекса и `RAGService`
(retrieve → rerank → synthesize).

**Обоснование:**

- Готовые интеграции с Qdrant и HuggingFace-эмбеддингами.
- Гибкая настройка чанкинга (`RAG_CHUNK_SIZE=512`, `RAG_CHUNK_OVERLAP=64`).
- Поддержка реранкера без переписывания пайплайна.
- Есть демо-версия «RAG руками» (`rag_baremetal.py`) — для сравнения и
  объяснения внутренностей на защите.

**Альтернативы:**

| Решение | Почему не выбрано |
|---|---|
| LangChain Retrieval | Менее удобен для чистого RAG без агента |
| Свой пайплайн | Лишняя работа, теряется гибкость на этапе экспериментов |

**Эксперимент по чанкингу:** см. [chunking_experiment.md](chunking_experiment.md).

## 6. Параметры RAG

| Параметр | Значение | Обоснование |
|---|---|---|
| `RAG_CHUNK_SIZE` | 512 | Оптимум для технических инструкций: не рвёт смысл, влезает в контекст |
| `RAG_CHUNK_OVERLAP` | 64 | Сохраняет связность на границах чанков |
| `RAG_RETRIEVE_TOP_K` | 10 | Кандидатов из Qdrant — с запасом для реранкера |
| `RAG_RERANK_TOP_N` | 5 | Столько чанков идёт в контекст LLM |
| `RAG_SCORE_THRESHOLD` | 0.5 | Отсекает нерелевантные запросы (вне предметной области) |
| `RAG_USE_HYBRID` | false | Включается, если качество dense-поиска недостаточно |
| `RAG_RERANKER_MODEL` | BAAI/bge-reranker-v2-m3 | Локальный, мультиязычный, оптимизирован под русский |

## 7. API-слой: FastAPI

**Решение:** FastAPI с Pydantic-схемами, DI-провайдерами (`app/deps/`) и
lifespan-инициализацией.

**Обоснование:**

- **Async из коробки** — критично для параллельных вызовов LLM/Ollama.
- **Pydantic v2** — валидация запросов/ответов, автогенерация OpenAPI.
- **DI** — чистая архитектура, лёгкое тестирование.
- **Lifespan** — инициализация RAG, агента, подключений к БД/Qdrant до
  первого запроса.

**Альтернативы:**

| Решение | Почему не выбрано |
|---|---|
| Flask | Синхронный, нет нативной асинхронности |
| Django REST | Избыточен, тяжелее |
| Starlette (без FastAPI) | Больше ручной работы с валидацией |

## 8. Чат-интерфейс: Telegram (aiogram 3.x)

**Решение:** Telegram-бот на `aiogram 3.x` с inline-кнопками, FSM и обратным
каналом `/notify`.

**Обоснование:**

- **Привычен пользователям** — не нужно ставить отдельное приложение.
- **FSM** — удобно для пошаговых сценариев (например, подтверждение письма).
- **Inline-клавиатуры** — кнопки «Отправить», «Отмена» для HIL.
- **Обратный канал** — backend может инициировать сообщение (алерты,
  эскалации) через `bot/web.py`.
- **Rate limiting** и стриминг токенов реализуются штатно.

**Альтернативы:**

| Решение | Почему не выбрано |
|---|---|
| Web UI (React/Vue) | Дольше разрабатывать, нужен хостинг, не решает задачу |
| CLI | Не для конечных пользователей техподдержки |
| MS Teams / Slack | Нет в контуре заказчика |

## 9. Хранение данных

| Слой | Решение | Обоснование |
|---|---|---|
| Чаты | PostgreSQL (`asyncpg`) | Надёжность, транзакции, JSONB для метаданных |
| Чекпоинты агента | PostgreSQL | Одна БД с чатами, restart-safe |
| Кеш LLM | Redis | TTL, атомарные операции |

## 10. Оценка качества: RAGAS

**Решение:** RAGAS с судьёй GPT-4o-mini через прокси (`EVAL_JUDGE_URL`).

**Обоснование:**

- **Стандарт индустрии** — метрики признаются академическим сообществом.
- **Шесть метрик** покрывают все аспекты RAG: генерацию, поиск, цитирование.
- **Golden dataset** из 15 вопросов — репрезентативно для дипломного проекта.
- **Внешний судья.** Судья отделён от production-LLM: если оценивать
  локальной моделью, получим завышенные оценки (self-preference bias).
- **Артефакты.** Каждый прогон — CSV в `tests/eval/results/{timestamp}_{label}.csv`,
  что даёт временной ряд метрик.

**Результаты:** см. [quality_report.md](quality_report.md).

**Альтернативы:**

| Решение | Почему не выбрано |
|---|---|
| DeepEval | Меньше готовых метрик, менее стандартизирован |
| TruLens | Требует отдельного UI, сложнее интеграция |
| Своя оценка | Дороже, субъективнее, не признаётся комиссией |

## 11. Модерация входящих сообщений

**Решение:** каскад — regex-блоклист (`regex_rules.py`) → LLM-модерация
(локальная или внешний судья, `MODERATION_USE_OPENAI`).

**Обоснование:**

- **Дёшево.** Regex отсекает большую часть мусора без вызова LLM.
- **Гибко.** LLM разбирает неоднозначные случаи (обфускация, контекст).
- **Локально.** Модерация не требует внешних API.

**Альтернативы:**

| Решение | Почему не выбрано |
|---|---|
| Только regex | Пропускает обфусцированные запросы |
| Только LLM | Дороже, медленнее, избыточно для 90% случаев |
| Внешний content-filter | Не подходит для on-premise |

## 12. Медиа: Vision + Whisper + PDF/DOCX

**Решение:** `media_processor.py` обрабатывает изображения (Vision),
голосовые (Whisper), PDF и DOCX.

**Обоснование:**

- Пользователи техподдержки **часто присылают скриншоты** ошибок.
- **Голосовые сообщения** удобны с телефона.
- **Вложения в письмах** (PDF/DOCX) — типовой кейс HelpDesk.
- Всё локально: Whisper через `faster-whisper`, Vision — через ту же
  Ollama-модель (`VISION_MODEL`).

---

## 13. Email: Yandex SMTP

**Решение:** `aiosmtplib` + Yandex SMTP, вложения через `email_service.py`.

**Обоснование:**

- Yandex — **корпоративный стандарт** заказчика.
- Пароль приложения — безопаснее основного пароля.
- Async-отправка не блокирует event loop.

**Альтернативы:** Exchange, Mail.ru — не приняты в контуре.

---

## 14. Трейсинг: Phoenix / OTLP (опционально)

**Решение:** `setup_tracing()` с флагом `PHOENIX_ENABLED=false` по умолчанию.

**Обоснование:**

- **OpenTelemetry-совместимо** — можно переключиться на Jaeger/Tempo.
- **Локальный UI** (`phoenix:6006`) — не уходит наружу.
- **Отключается по умолчанию** — экономит ресурсы, не мешает production.

## 15. Развёртывание: Docker Compose

**Решение:** `compose.yaml` из 7 сервисов: `app`, `bot`, `postgres`, `redis`,
`qdrant`, `phoenix`, `ollama`.

**Обоснование:**

- **Одна команда** `docker compose up -d` — критично для защиты и передачи
  заказчику.
- **Изолированные сервисы** — можно обновлять по отдельности.
- **Healthchecks и depends_on** — корректный порядок старта.

**Альтернативы:**

| Решение | Почему не выбрано |
|---|---|
| Kubernetes | Overkill для одной ноды |
| Голый Python + systemd | Дольше настраивать, хуже переносится |
| Podman Compose | Меньше экосистема, нет выгоды |

---

## 16. Что осознанно НЕ делалось

- **Мультиагентность.** Один агент с инструментами покрывает задачу,
  мультиагентность усложнила бы отладку без выигрыша.
- **Fine-tuning LLM.** 4B-модель + RAG дают достаточное качество; дообучение
  требует данных и GPU-времени, которых нет.
- **Кластеризация Qdrant.** 668 точек — далеко до порога, при котором
  нужен шардинг.
- **Web UI.** Telegram закрывает потребности пользователей.
- **Облачные провайдеры LLM.** Нарушают принцип on-premise.
- **Собственная vector DB.** Qdrant зрелее и поддерживается.

## 17. Итоговые метрики (RAGAS)

| Метрика | 1-й запуск | 3-й запуск | Δ |
|---|---|---|---|
| Faithfulness | 0.876 | **0.933** | +0.06 |
| Answer Relevancy | 0.524 | **0.638** | +0.11 |
| Context Precision | 0.734 | **0.906** | +0.17 |
| Context Recall | 0.667 | **0.933** | +0.27 |
| Factual Correctness | 0.230 | **0.585** | +0.36 |
| Has Citation | — | 15/15 | ✅ |

Рост достигнут за счёт:

- улучшения промптов (в том числе few-shot классификатора);
- корректной настройки чанкинга (512/64);
- включения реранкера на отдельных прогонах.

Подробности — в [quality_report.md](quality_report.md).

## 18. Ограничения и риски

### 18.1 Функциональные ограничения

| # | Ограничение | Влияние | Митигация |
|---|---|---|---|
| 1 | Система отвечает **только по загруженным документам**. За пределами корпуса — отказ | Пользователь не получит ответа на «свободный» вопрос | Порог `RAG_SCORE_THRESHOLD=0.5` + вежливый отказ с предложением переформулировать |
| 2 | Нет интеграции с 1С:ERP напрямую (только через документы) | Нельзя выполнить действие в системе | Задел: инструменты LangGraph; в плане развития — REST-коннектор |
| 3 | Нет авторизации в API (`/agent/*` открыты внутри контура) | Нельзя выставить наружу | Разворачивается только в локальной сети; для внешнего доступа — reverse-proxy с auth |
| 4 | Один язык интерфейса (русский) | Неудобно для иностранных сотрудников | Локализация — в плане развития |
| 5 | Нет полнотекстового поиска по чатам | Нельзя «вспомнить» старый диалог | Метрика в плане развития |

### 18.2 Технические риски

| # | Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|---|
| 1 | **Ollama падает** (OOM, сбой GPU) | Средняя | Высокое (нет LLM) | `restart: unless-stopped`, healthcheck, fallback на CPU |
| 2 | **Закончится VRAM** при одновременном вызове LLM + Vision + Whisper | Средняя | Среднее | Последовательная обработка, `VISION_MODEL` = основной LLM (кэш) |
| 3 | **Qdrant теряет данные** (сбой volume) | Низкая | Высокое | Volume + возможность переиндексации одной командой |
| 4 | **Модель `frob/qwen3.5-instruct:4b` удалена** из Ollama Hub | Низкая | Высокое | Зафиксировать версию/тег; локальный `models/` backup |
| 5 | **Postgres переполнится** (история чатов) | Низкая | Среднее | Периодическая очистка, лимит `CHAT_CONTEXT_WINDOW` |
| 6 | **Рост корпуса** выше 10 000 документов | Низкая | Среднее | Индексация батчами, при необходимости — шардинг Qdrant |
| 7 | **Утечка `BOT_TOKEN` / `INTERNAL_TOKEN`** | Низкая | Критичное | `.env` в `.gitignore`, ротация токенов, `X-Internal-Token` |
| 8 | **Судья RAGAS недоступен** (proxyapi.ru) | Средняя | Низкое (только оценка) | Оценка — вне production-контура; fallback на локального судью |
| 9 | **Долгий ответ** при большом контексте | Средняя | Среднее | Стриминг (`/agent/stream`), `LLM__REQUEST_TIMEOUT=180` |
| 10 | **Галлюцинации LLM** на нерелевантном контексте | Средняя | Высокое | Faithfulness = 0.933; порог релевантности; обязательное цитирование |

### 18.3 Организационные риски

| # | Риск | Митигация |
|---|---|---|
| 1 | Заказчик не готов к on-premise GPU | Документация по требованиям, возможность работы на CPU (медленнее) |
| 2 | Нет штатного администратора Qdrant | Один сервис, стандартные операции, бэкап volume |
| 3 | Пользователи не доверяют ИИ-ответам | Всегда показываем источники + Has Citation 15/15 |
| 4 | Отсутствие процесса обновления корпуса | Скрипт `scripts/ingest.py` + описание в README |

## 19. План развития

### 19.1 Краткосрочный (1–3 месяца)

- **Смоук-тесты и CI.** Добавить `tests/test_health.py`, `tests/test_rag.py`,
  настроить GitHub Actions (линт + pytest на PR).
- **Метрики production.** Счётчики Prometheus для `/agent/chat`, `/rag/query`:
  latency, error rate, cache hit rate.
- **Расширение golden dataset** с 15 до 50 вопросов. Целевые метрики:
  Faithfulness ≥ 0.95, Answer Relevancy ≥ 0.75.
- **Логирование пользовательских отказов** (запросов ниже `RAG_SCORE_THRESHOLD`)
  — для расширения корпуса.
- **Alembic-миграции** для схемы чатов (сейчас частично ручные).

### 19.2 Среднесрочный (3–6 месяцев)

- **Интеграция с 1С:ERP.** REST-коннектор для выполнения базовых действий
  (создание заявки, статус, эскалация) как инструментов LangGraph.
- **Гибридный поиск** (`RAG_USE_HYBRID=true`) — dense + BM25 через
  `Qdrant/bm25`. Ожидаемый прирост Context Recall.
- **Реранкер по умолчанию.** Включить `bge-reranker-v2-m3` на всех запросах,
  замерить прирост Factual Correctness.
- **Мультимодальность в ответе.** Не только принимать голосовые/картинки,
  но и **отвечать** голосом (TTS через локальные модели).
- **История и поиск по чатам.** Полнотекстовый индекс в Postgres
  (`tsvector`) для админ-панели.
- **Роли и доступы.** Разграничение: сотрудник, оператор, администратор.
- **Экспорт диалога** в PDF для эскалации в HelpDesk.

### 19.3 Долгосрочный (6–12 месяцев)

- **Дообучение на исторических тикетах HelpDesk.**
  LoRA/QLoRA для `qwen` на русскоязычных обращениях. Целевые метрики:
  Answer Relevancy ≥ 0.85, Factual Correctness ≥ 0.75.
- **Мультиагентная схема.** Отдельные агенты: «поиск», «действие»,
  «эскалация», «модерация». Оркестрация через LangGraph.
- **Переход на 7B–14B модель.** При апгрейде GPU (24 ГБ) — `Qwen2.5:14b`
  или `Llama-3.1-8b-instruct`.
- **Локализация.** EN-версия для холдинга «Трансмашхолдинг».
- **Аналитика для руководства.** Дашборд: топ-вопросы, отказанные запросы,
  частота эскалаций, среднее время ответа.
- **A/B-платформа.** Возможность включать/выключать реранкер, гибрид,
  разные промпты на живом трафике.
- **Оценка в реальном времени.** Автоматическая RAGAS-оценка на случайной
  выборке production-запросов.

### 19.4 Что НЕ планируется

- **Отказ от on-premise.** Это принципиальное требование заказчика.
- **Замена Telegram на Web UI.** Telegram выбран осознанно.
- **Полный переход на облачного судью RAGAS.** Судья — только для оценки,
  в production-контуре ему не место.
- **Микросервисная декомпозиция.** Монолит + Docker Compose оптимальны
  для текущего масштаба.

## 20. Заключение

Все ключевые технические решения приняты по принципу **«минимально
достаточная сложность при максимальной объяснимости»**:

- Стек **on-premise** — данные не покидают контур предприятия.
- Каждый компонент выбран под конкретные ограничения (12 ГБ VRAM,
  один сервер, русскоязычный корпус).
- Каждое решение подтверждено **экспериментом или метрикой**
  (RAGAS, cosine-vs-dot, chunking).
- Система **воспроизводима** — `docker compose up -d` на чистой машине.
- Заложен **чёткий план развития** без пересмотра архитектурных принципов.

Проект готов к защите и передаче в опытную эксплуатацию в службе УИТ
АО «УК «БМЗ».
